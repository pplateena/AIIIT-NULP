# API Limitations Report: Free Tier LLM Services

## Лабораторна робота №4 - Аналіз обмежень безкоштовних API

**Дата:** 16 грудня 2024
**Система:** GT New Horizons RAG Pipeline
**Тестовані провайдери:** Google Gemini API (Free Tier), Anthropic Claude API (Free Tier)

---

## 1. Виявлені проблеми з безкоштовними API

### 1.1 Google Gemini API (Free Tier)

#### Ліміти та обмеження:
- **Запити за хвилину (RPM):** 15 requests/minute
- **Токени за хвилину (TPM):** 1,000,000 tokens/minute
- **Запити за день (RPD):** 1,500 requests/day
- **Скидання лімітів:**
  - Хвилинні: кожні 60 секунд
  - Денні: опівночі за Pacific Time (PT)

#### Практичний досвід:
```
Початок тестування: 21:26
Успішно виконано: 21 запит
Помилка квоти: після ~26 загальних запитів до API
Код помилки: 429 "You exceeded your current quota"
```

#### Виміряна продуктивність:
- **Середній час відповіді:** 6-10 секунд на запит
- **Максимальна кількість тестів без затримки:** ~15 (1 хвилина)
- **Рекомендована затримка між запитами:** 5+ секунд (12 запитів/хвилину)

#### Типові помилки:

```json
{
  "error": {
    "code": 429,
    "message": "You exceeded your current quota, please check your plan and billing details",
    "status": "RESOURCE_EXHAUSTED"
  }
}
```

### 1.2 Anthropic Claude API (Free Tier)

#### Обмеження:
- **Безкоштовний рівень:** Дуже обмежений (вимагає налаштування платіжних даних)
- **Rate limits:** Варіюються залежно від тарифного плану
- **Проблема:** Потребує кредитної картки навіть для безкоштовного тестування

## 2. Вплив обмежень на тестування RAG-системи

### 2.1 Часові витрати

**Без обмежень (теоретично):**
- 21 тест × ~7 сек = **~2.5 хвилини**

**З безкоштовними API:**
- 21 тест × (7 сек + 5 сек затримка) = **~4.2 хвилини**
- Ризик перевищення квоти: **високий**
- Необхідність чекати скидання: **до 24 годин**

### 2.2 Неможливість масштабування

#### Обмеження для повноцінного тестування:
```
Тестовий набір: 21 питання
Бажана кількість ітерацій: 3-5 (для оцінки стабільності)
Загальна потреба: 63-105 запитів

Денний ліміт Gemini: 1,500 запитів
Реальна доступність: ~26 запитів (через інші взаємодії)
```

**Висновок:** Навіть для невеликого тестового набору безкоштовні ліміти недостатні для повноцінного дослідження.

### 2.3 Проблеми з відтворюваністю результатів

#### Виклики:
1. **Денні ліміти:** Неможливо повторити експеримент в той самий день
2. **Залежність від часових поясів:** Скидання опівночі PT (UTC-8)
3. **Непередбачуваність:** Важко планувати експерименти
4. **Спільне використання квоти:** Всі запити в системі споживають один ліміт

## 3. Метрики використання API

### 3.1 Статистика успішного тестування

```
Всього запитів до API: ~26
Успішних відповідей: 21 (80.8%)
Помилок через квоту: 5+ (19.2%+)
Середня довжина відповіді: ~150-200 слів
Середня кількість джерел: 3-4 на запит
```

### 3.2 Якість відповідей (успішних)

Згідно з автоматичною оцінкою:
```
Quality Score: 21/21 успішних відповідей
Topic Coverage: Висока (>70% очікуваних тем покрито)
Response Length: Адекватна (100-300 слів)
Source Relevance: Хороша (0.6-0.8 середня релевантність)
```

## 5. Практичні рекомендації

### 5.1 Стратегії роботи з обмеженнями

#### Для розробки:
1. **Кешування відповідей:** Зберігати результати для повторного використання
2. **Інкрементальне тестування:** Зберігати прогрес після кожного запиту
3. **Локальні моделі для дебагінгу:** Ollama для швидких ітерацій
4. **Продакшн API для фінального тестування:** Google Gemini/Claude для якості

#### Для тестування:
```python
# Приклад затримки для уникнення rate limits
import time

def safe_api_call(query, delay=5):
    response = api.generate(query)
    time.sleep(delay)  # 5 сек = 12 запитів/хв < 15 RPM limit
    return response
```

### 5.2 Оптимізація використання квоти

#### Зменшення споживання:
- **Batch processing:** Групувати запити
- **Prompt optimization:** Коротші промпти = менше токенів
- **Response limits:** Обмежити max_tokens
- **Smart caching:** Уникати повторних запитів

#### Приклад конфігурації:
```python
# Економна конфігурація
config = {
    "max_tokens": 500,      # замість 2048
    "temperature": 0.7,     # детермінованість
    "cache_responses": True # кешування
}
```

## 6. Висновки

### 6.1 Ключові знахідки

1. **Безкоштовні API непридатні для серйозного дослідження**
   - Денний ліміт вичерпується за ~17 тестових запитів
   - Неможливо провести повноцінну оцінку системи
   - Відсутність можливості повторних експериментів

2. **Необхідність гібридного підходу**
   - Локальні моделі для розробки та дебагінгу
   - Cloud API для фінальної оцінки якості
   - Інкрементальне збереження для уникнення втрати даних

3. **Часові та фінансові витрати**
   - Безкоштовно ≠ ефективно
   - Втрати часу на очікування скидання квот
   - Платні плани необхідні для продуктивної роботи

### 6.2 Рекомендації для лабораторної роботи

#### Для студентів:
- **Використовувати локальні моделі** (Ollama) для основної розробки
- **Зберігати всі проміжні результати** (dialogue_history.json)
- **Планувати використання API заздалегідь** (обмежена кількість експериментів)
- **Документувати всі спроби** для звіту

#### Для викладачів:
- **Надати доступ до спільного API ключа** з більшою квотою, або
- **Рекомендувати локальні альтернативи** як основний інструмент, або
- **Дати розширений дедлайн** для очікування скидання квот

## 7. Технічна реалізація обхідних шляхів

### 7.1 Резюмований код для збереження прогресу

```python
class ResumableRAGTester:
    def run_resumable_tests(self):
        for test in tests:
            try:
                result = self.run_test(test)
                self.save_progress(result)  # Зберегти після кожного!
            except QuotaExceeded:
                print("Quota exceeded. Resume with:")
                print(f"  --resume {self.results_file} --start {current_test}")
                break
```

### 7.2 Переваги інкрементального збереження

- ✅ **Немає втрати даних** при перевищенні квоти
- ✅ **Можливість резюмувати** з будь-якого моменту
- ✅ **Незалежність від тривалості тестування**
- ✅ **Захист від збоїв** (мережа, система)

```

Запланована: 21 тест
```
